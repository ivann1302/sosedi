# Инструкция для работы с Codex в проекте `sosedi`

Этот файл описывает, как взаимодействовать с Codex при работе над проектом `sosedi`.

---

# О проекте

Проект представляет собой корпоративный промо-сайт компании.

Стек:

* Next.js (App Router)
* TypeScript
* React
* SCSS

Особенности проекта:

* Backend отсутствует.
* База данных отсутствует.
* Авторизация отсутствует.
* Основная задача сайта — привлечение клиентов и SEO.
* Максимальный приоритет имеют скорость загрузки, простота поддержки и качество пользовательского интерфейса.

---

# Основные принципы разработки

## Простота важнее абстракций

Всегда выбирать самое простое рабочее решение.

Не создавать без необходимости:

* дополнительные хуки;
* контексты;
* сервисные слои;
* фабрики;
* провайдеры;
* сложные паттерны проектирования.

Следовать принципам:

* KISS
* YAGNI
* DRY

Перед реализацией проверять:

* можно ли сделать проще;
* можно ли удалить часть кода;
* можно ли решить задачу без новой зависимости.

---

## Минимум зависимостей

Не устанавливать новые библиотеки без веской причины.

Перед добавлением зависимости:

1. объяснить зачем она нужна;
2. предложить вариант без неё;
3. использовать библиотеку только если выгода очевидна.

Предпочитать:

* возможности браузера;
* возможности React;
* возможности Next.js.

---

## Архитектура проекта

Использовать структуру:

src/
├── app/
├── components/
│ ├── ui/
│ ├── sections/
├── lib/
├── hooks/
├── types/
├── assets/

Правила:

* ui — переиспользуемые компоненты;
* sections — секции страниц;
* hooks — только при реальном переиспользовании;
* lib — утилиты и вспомогательные функции;
* types — общие типы.

Не создавать директории заранее.

---

## Работа с компонентами

Каждый компонент должен иметь одну ответственность.

Не создавать отдельный компонент ради нескольких строк JSX.

Если компонент используется один раз и не переиспользуется — допускается оставить его внутри секции.

Предпочитать читаемость переиспользованию.

---

## TypeScript

Всегда использовать строгую типизацию.

Запрещено:

* any;
* избыточные type assertions;
* отключение проверок TypeScript.

Предпочитать:

* type вместо interface;
* явные типы для сложных структур данных.

---

## Next.js

Использовать App Router.

По умолчанию использовать Server Components.

Добавлять "use client" только если действительно нужны:

* useState;
* useEffect;
* браузерные API;
* интерактивные элементы.

Не превращать компонент в клиентский без необходимости.

---

## Tailwind CSS

Использовать Tailwind напрямую.

Не создавать преждевременные абстракции над классами.

Сначала понятность.

Потом переиспользование.

---

## Производительность

Для каждой задачи учитывать:

* размер бандла;
* количество Client Components;
* количество JavaScript на странице;
* Core Web Vitals.

Не использовать без необходимости:

* useMemo;
* useCallback;
* React.memo.

---

## SEO

Каждая страница должна иметь:

* title;
* description;
* Open Graph;
* корректную структуру заголовков;
* семантическую HTML-разметку.

Использовать Metadata API Next.js.

Следить за:

* accessibility;
* Lighthouse Score;
* индексируемостью страниц.

---

## Адаптивность

Подход mobile-first.

Обязательно проверять:

* мобильные устройства;
* планшеты;
* десктоп.

Использовать стандартные брейкпоинты Tailwind.

---

# Как ставить задачи

* Формулируйте цель через ожидаемый результат.
* Для багов указывайте шаги воспроизведения.
* Если задача только на обсуждение — пишите "не изменяй файлы".
* Если есть ограничения, указывайте их сразу.

---

# Как Codex должен работать

Перед внесением изменений:

1. прочитать `brandbook/brandbook.md` и `DESIGN_SYSTEM.md`, учитывать актуальный брендбук при каждой задаче; затем изучить существующую структуру;
2. найти похожие реализации;
3. предложить минимальное решение.

Запрещено:

* выполнять git reset;
* выполнять git checkout;
* удалять пользовательские изменения;
* массово рефакторить несвязанный код.

---

# Работа с кодом

Предпочитать существующие паттерны проекта.

Не переписывать код без необходимости.

## Обязательный брендбук

Актуальная целевая структура главной страницы: [HOME_PAGE_STRUCTURE.md](HOME_PAGE_STRUCTURE.md), утверждена пользователем 22 сентября 2026 года. Перед изменениями главной читать этот документ и соблюдать порядок секций, тексты и задачи блоков. Он имеет приоритет над прежними планами `HOME_PAGE_PLAN.md` и `brandbook/REDESIGN_PLAN.md` в вопросах структуры и содержания главной.

История редизайна и ранее выполненных этапов: [brandbook/REDESIGN_PLAN.md](brandbook/REDESIGN_PLAN.md). Приведённый там статус завершения относится к прежнему проходу и не означает, что новая целевая структура уже реализована.

При начале каждой задачи читать [brandbook/brandbook.md](brandbook/brandbook.md) и [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md). Для изменений визуального стиля, страниц, секций, UI, текстов и медиа также просматривать [brandbook/brandbook.png](brandbook/brandbook.png) и относящиеся к задаче изображения из `brandbook/`.

`brandbook/brandbook.md` — основной источник визуальных правил. `brandbook/brandbook.png` — основной визуальный ориентир; остальные PNG — дополнительные референсы, кроме явно выбранных логотипов ниже. При расхождении текста и картинок использовать значения и ограничения из Markdown.

Пользователь выбрал логотипы «Всё рядом»: вариант 1 — основной, вариант 3 — дополнительный. Правила и готовые файлы: [brandbook/logos/README.md](brandbook/logos/README.md). Использовать основной знак в шапке, круглый — для дополнительных размещений и иконки сайта. Вариант 2 не использовать. Название в интерфейсе — «Всё рядом»; техническое имя проекта `sosedi` и контактные адреса не менять без отдельной задачи.

`DESIGN_SYSTEM.md` дополняет брендбук правилами реализации, доступности, SEO и адаптивности. При конфликте визуальных рекомендаций приоритет у брендбука; прямые указания пользователя имеют приоритет над обоими документами.

Для каждой затронутой секции сверять палитру, типографику, композицию, отступы, CTA, фотостиль и количество декора с брендбуком. В итоговом ответе по UI-задаче кратко отмечать соответствие и оставшиеся отклонения. Для задач без визуальных изменений учитывать брендбук как контекст, не выполнять попутный редизайн.

Примеры каталога, авторизации, OTP, бронирования и магазинов приложений в брендбуке не меняют функциональный объём проекта. Не добавлять эти функции, неработающие CTA, вымышленные отзывы или показатели без отдельной задачи и реальных данных.

Не создавать технический долг ради быстрого решения.

Не оставлять:

* TODO;
* заглушки;
* временные решения;

без явного указания пользователя.

# Особое правило для лендингов и промо-сайтов

Если задачу можно решить:

* HTML;
* CSS;
* Server Component;

то не использовать JavaScript.

Минимизировать клиентский код.

Сайт должен оставаться максимально быстрым, простым и SEO-оптимизированным.

Структура сайта
Цель этапа — начать набор авторитета домена и получать органический трафик до выхода приложения.

Промо-сайт:
• Главная страница.
• Описание продукта.
• FAQ.
• CTA-блоки.
• Блок скачивания приложения.
• Блог.
• Страница для бизнеса.
• Юридические страницы.
